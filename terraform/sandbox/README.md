# Per-sandbox Terraform stack

One `terraform apply` of this directory == one CiviForm sandbox.

Everything shared — VPC, RDS, ALB, ECS cluster, KMS key, placeholder secrets —
lives in [`../`](../) and arrives here as input variables. This stack creates
only what is genuinely per-sandbox: a task definition, an ECS service, two S3
buckets, four secrets, and one ALB listener rule.

## Applying by hand

```bash
terraform init \
  -backend-config="bucket=civiform-sandbox-tfstate" \
  -backend-config="key=sandboxes/sb-a1b2c3d4/terraform.tfstate" \
  -backend-config="region=us-east-1" \
  -backend-config="use_lockfile=true"

terraform apply -var-file=sandbox.tfvars.json
```

> The database must exist first. See "Ordering" below.

## Where the pieces come from

| Concern                                                     | Source                                           |
| ----------------------------------------------------------- | ------------------------------------------------ |
| Task definition, container definition, task execution role  | `civiform_app` module, cloud-deploy-infra        |
| ECS service, target group, task security group, autoscaling | `ecs_fargate_service` module, cloud-deploy-infra |
| Buckets, secrets, listener rule                             | This directory                                   |
| VPC, subnets, RDS, ALB, cluster, KMS, placeholders          | Platform stack                                   |

Both upstream modules are pinned to commit
`d85c413549bfcbe0be7f1c6cacc4a65ebe702706`.

> [!IMPORTANT]
> Terraform resolves `source` before variables and locals exist, so the ref
> cannot be factored into a local. It is a literal in **both** module blocks in
> `main.tf`. Bump both together — nothing warns you if they drift.

A commit SHA rather than a branch is deliberate: with a moving ref, two
sandboxes created a week apart would silently run different infrastructure.

## Ordering

The builder must do these in order, and the ordering is not arbitrary:

1. **Create the database and its role over JDBC** against the shared RDS.
2. **Allocate a listener priority** from the `sandbox_listener_priority_seq`
   Postgres sequence.
3. **`terraform apply`** with those values.
4. **Poll** the target group until healthy.

Step 1 cannot move after step 3. The container health-checks against the
database on startup, and the ECS service has a deployment circuit breaker that
gives up after 10 failed task launches — so a missing database does not
manifest as a retry, it manifests as a failed deployment that rolls back.

`SECRET_KEY` and `CIVIFORM_API_SECRET_SALT` are _not_ passed in; they are
generated by Terraform in `secrets.tf`, since nothing needs them before apply.

## Reachability

There is no DNS resource here. Cloudflare holds a wildcard `*.<base_domain>`
record ("DNS only", no proxy) pointing at the shared ALB, and the ACM
certificate covers the same wildcard. A sandbox becomes reachable the moment
its listener rule exists — no record to create, no propagation to wait for, no
certificate to issue.

## Teardown

`terraform destroy` removes everything in this stack. Two things it does _not_
do, both on purpose:

- **The database is not dropped.** It lives on the shared RDS instance, which
  this stack does not manage. The builder drops it over JDBC after destroy.
- **CloudWatch logs are not removed.** The log group is shared and owned by the
  platform stack; this sandbox's streams age out under the group's 30-day
  retention.

Both S3 buckets set `force_destroy = true`, without which destroy fails on a
bucket that any demo will have written to.

## Cost

Roughly $22/month per running sandbox, dominated by the Fargate task. Shared
infrastructure (ALB, RDS, NAT gateway, KMS) is not included — that cost is
fixed regardless of how many sandboxes exist, which is the entire argument for
the shared-platform design.
